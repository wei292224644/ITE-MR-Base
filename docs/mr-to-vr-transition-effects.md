# MR → VR 丝滑转场方案

> 状态：方案摘要  
> 适用平台：PICO、Meta Quest 及其他 Android 一体机  
> 更新日期：2026-08-04

## 1. 目标

应用开始时显示真实环境和少量虚拟内容，随后通过连续、舒适且有叙事感的视觉过程，将体验转变为完全封闭的 VR 世界。

MR → VR 比两个完整虚拟世界之间的切换更简单：真实环境通常由系统 Passthrough/VST 合成层提供，不需要加载和渲染一套“场景 A”几何。VR 中的不透明几何会自然遮挡位于背景的真实画面。

本方案仍需解决三个问题：

- VR 场景必须在视觉转场结束前加载并初始化完成。
- 关闭 Passthrough 前，玩家视野必须已被可靠遮挡。
- PICO 与 Quest 的平台 API 不同，业务层不能直接依赖某一家 SDK。

## 2. 核心原则

不要尝试直接给 Passthrough 画面应用普通 Unity Shader。跨平台的稳定做法是：

```text
Passthrough 保持在背景
    ↓
VR 世界通过虚拟几何、遮罩和特效逐渐显现
    ↓
VR 内容完全覆盖视野
    ↓
调用平台适配层关闭 Passthrough
    ↓
移除转场特效，进入正常 VR 渲染
```

建议提供统一接口：

```csharp
public interface IXRPassthroughService
{
    bool IsEnabled { get; }
    Task SetEnabledAsync(bool enabled);
}
```

分别由 PICO 和 Quest 适配器实现。视觉过渡由 Unity 场景负责，不依赖各平台是否支持相同的 Passthrough 透明度或后处理能力。

## 3. 转场方式总览

| 方式 | 视觉表现 | 实现复杂度 | 移动 XR 性能 | 隐藏加载能力 | 推荐场景 |
|---|---|---:|---:|---:|---|
| 地面向上重构 | 世界从地面生长并封闭 | 中 | 良好 | 中 | 虚实空间结构接近 |
| 径向消融 | 从中心向四周扩散 | 低至中 | 良好 | 中 | 祭坛、装置、仪式触发 |
| 扫描波转换 | 扫描线前后分别为 MR/VR | 中 | 良好 | 中 | 隧道、走廊、队列体验 |
| 雾化转换 | 浓雾覆盖后显露 VR | 低至中 | 良好 | 很强 | 虚实空间差异大 |
| 结晶/体素化 | 粒子聚合形成世界 | 高 | 较高风险 | 强 | 强视觉演出、短时使用 |
| 裂缝/Portal 扩张 | 多个窗口扩大并连接 | 高 | 中至较高 | 中 | 空间撕裂、异世界题材 |
| 黑场/光幕闭合 | 视野短暂被完全覆盖 | 低 | 最稳定 | 很强 | 兜底、低性能设备 |

## 4. 方案一：地面向上重构

### 4.1 表现

```text
真实地面
→ 出现虚拟网格和能量纹路
→ VR 地面覆盖真实地面
→ 墙体、建筑和装饰由下向上生成
→ 天花板或穹顶闭合
→ 关闭 Passthrough
```

### 4.2 优点

- 玩家脚下参照始终稳定，舒适度较好。
- 可以自然维持真实地面与虚拟地面的连续性。
- 场景内容可按地面、主体、天空的顺序分阶段初始化。
- 适合遗迹苏醒、数字世界构建和神殿显现等叙事。

### 4.3 实现要点

- 使用世界空间高度遮罩控制 VR 材质显现。
- 在高度遮罩上叠加 Noise，避免边缘过于机械。
- 地面应最先可见，碰撞和交互状态与视觉状态分开管理。
- 穹顶或封闭空间 Mesh 最后覆盖天空，再关闭 Passthrough。

## 5. 方案二：径向消融

### 5.1 表现

从一个祭坛、法器、按钮或空间锚点开始，VR 世界以球形或圆柱形范围向外扩张。

```hlsl
float d = distance(positionWS, _TransitionCenter);
float mask = smoothstep(
    _TransitionRadius - _TransitionFeather,
    _TransitionRadius + _TransitionFeather,
    d);
```

VR 内容只显示在遮罩内部，边缘叠加发光、噪声、粒子和冲击波。

### 5.2 优点

- 实现直接，控制参数少。
- 具有明确的触发中心和传播方向。
- 易于同步到多个客户端。
- 适合与交互物、手势或剧情事件结合。

### 5.3 注意事项

- 不需要对真实画面做反向裁剪，只需要逐渐显示 VR 内容。
- 球面经过玩家头部时应使用宽而柔和的边缘，避免高亮闪烁。
- 转场完成后应关闭消融 Shader 分支或切回普通材质。

## 6. 方案三：扫描波转换

### 6.1 表现

使用一个平面或弧形扫描波从场馆一侧向另一侧推进：

```text
扫描线前方：MR
扫描线经过区域：发光和重构特效
扫描线后方：VR
```

### 6.2 优点

- 非常适合狭长隧道、走廊和队列式多人体验。
- 所有玩家能理解统一的变化方向。
- 可以让扫描线与玩家前进速度、门或移动平台同步。

### 6.3 实现要点

- 使用世界空间平面距离或点积生成遮罩。
- 扫描线应有足够宽的过渡区域，不要只做一条高亮细线。
- 多人模式由统一网络时间驱动扫描位置。

## 7. 方案四：雾化转换

### 7.1 表现

```text
MR 环境出现薄雾和粒子
→ 雾逐渐增浓并遮住真实空间
→ 完全遮挡时关闭 Passthrough
→ VR 场景完成激活
→ 雾逐渐散去，展示完整 VR 世界
```

### 7.2 优点

- 最适合隐藏不确定的加载和初始化时间。
- 能掩盖真实场馆与 VR 场景几何完全不同的问题。
- 适合梦境、传送、烟尘、云海和灵气等主题。

### 7.3 实现要点

- 移动头显不必使用昂贵的全分辨率体积雾。
- 可使用少量粒子、深度淡化平面、穹顶和颜色层组合模拟。
- 避免大量透明粒子覆盖整个双眼画面造成 Overdraw。
- 必须准备一个不依赖加载成功的完全遮挡层作为兜底。

## 8. 方案五：空间结晶或体素化

### 8.1 表现

真实空间上先出现扫描网格，随后碎片、晶体、三角形或体素逐渐聚合成 VR 世界。

```text
空间扫描
→ 结构网格化
→ 粒子/碎片聚合
→ VR 几何形成
→ Passthrough 关闭
```

### 8.2 优点

- 演出感强，适合重要剧情节点。
- 可以将场景加载包装为“世界正在生成”。

### 8.3 风险

- 粒子、透明材质和双眼 Overdraw 成本较高。
- 大量独立碎片会增加 CPU、动画和 Draw Call 压力。
- PICO/Quest 应优先使用 GPU Instancing、少量网格批次和预烘焙动画。

## 9. 方案六：空间裂缝或 Portal 扩张

### 9.1 表现

在墙壁、地面或空气中出现一个或多个 VR 窗口，窗口不断扩大并连接，最终覆盖整个空间。

### 9.2 优点

- 玩家可以提前窥见目标世界。
- 适合异世界、时空裂缝和传送门题材。
- 可与剧情对象和空间锚点形成强关联。

### 9.3 风险

- 多个 Portal 需要管理多个遮罩中心和融合边界。
- RenderTexture 或多次场景渲染会显著增加移动 XR 成本。
- 优先采用单场景几何遮罩；谨慎使用真正的第二相机 Portal。

## 10. 方案七：黑场、光幕或虹膜闭合

这是最简单且最可靠的技术兜底：

```text
视野边缘逐渐闭合或强光覆盖
→ 画面完全不透明
→ 关闭 Passthrough并完成场景切换
→ 视野重新打开
```

它的视觉冲击力较弱，但具有以下价值：

- 可以隐藏任意长度的加载过程。
- 内存和渲染成本最低。
- 可作为其他复杂转场失败或超时后的安全降级方案。

应使用舒适的渐变和固定在相机上的不透明几何层，避免突然闪白。

## 11. 推荐组合

本项目推荐采用“地面重构 + 径向消融 + 穹顶封闭”的组合：

```text
阶段 1：MR 中的交互物被触发
阶段 2：地面网格和环境音开始变化
阶段 3：径向消融从交互物向外扩散
阶段 4：VR 地面、建筑和墙体由下向上显现
阶段 5：能量穹顶扩张并完全覆盖玩家视野
阶段 6：关闭 Passthrough
阶段 7：移除遮罩和临时特效，进入普通 VR 渲染
```

如果真实空间和 VR 世界差异很大，在阶段 4 和阶段 5 之间加入雾化遮挡。

## 12. 推荐状态机

```csharp
public enum MrToVrTransitionState
{
    MixedReality,
    PreloadingVr,
    PrimingEffects,
    RevealingFloor,
    RevealingWorld,
    ClosingDome,
    WaitingForFullOcclusion,
    DisablingPassthrough,
    FinalizingVr,
    VirtualReality,
    Failed
}
```

状态机至少应保证：

- VR 场景未准备完成时不能关闭 Passthrough。
- Passthrough 未确认关闭时不能移除完全遮挡层。
- 加载失败时可以恢复 MR 或保持安全遮挡。
- 同一时间只允许一个转场任务执行。
- 转场可以记录耗时、掉帧和失败原因。

## 13. 与场景加载系统的配合

MR → VR 的视觉转场不能代替资源加载。推荐流程：

```text
MR Scene / Bootstrap Active
    ↓
预下载 VR 场景依赖
    ↓
Additive 加载 VR Scene
    ↓
完成必要初始化，VR Renderer 保持遮罩状态
    ↓
执行 MR → VR 视觉转场
    ↓
关闭 Passthrough
    ↓
清理转场特效和不再需要的 MR 内容
```

完整的场景加载和资源释放规则参见 [Unity 多场景无缝切换方案](unity-multi-scene-seamless-transition.md)。

## 14. Shader 实现建议

当前项目使用 URP，可建立统一的 `MRToVRReveal` Shader Graph Sub Graph，供 VR 场景材质复用。

推荐参数：

```text
_TransitionCenter
_TransitionRadius
_TransitionHeight
_TransitionPlane
_TransitionFeather
_EdgeWidth
_EdgeColor
_NoiseScale
_NoiseStrength
_TransitionMode
_TransitionEnabled
```

材质策略：

- 主体使用 Opaque + Alpha Clip，不使用长期半透明。
- 边缘发光和能量壳使用独立特效材质。
- 转场结束后关闭 `_TransitionEnabled` 或切换到普通材质变体。
- 所需 Shader Variant 必须提前预热，避免切换瞬间编译卡顿。

过渡阶段不建议直接依赖 Skybox。可以使用大型封闭穹顶 Mesh 参与遮罩；Passthrough 关闭后再切换到正常 Skybox。

## 15. 性能与舒适度

### 15.1 移动 XR 性能

- 控制透明粒子和全屏能量壳的 Overdraw。
- 避免为 Portal 使用第二台全分辨率双眼相机。
- 尽量使用单一全局遮罩参数，不为每个对象创建独立材质实例。
- 特效完成后关闭临时 Renderer、粒子和 Shader 分支。
- 在 PICO 和 Quest 真机上分别验证 GPU 与内存峰值。

### 15.2 舒适度

- 优先保持真实地面与 VR 地面的高度和朝向一致。
- 不要在转场时移动 XR Origin 或突然旋转世界。
- 避免球面经过头部时出现窄、高亮和高速闪烁边缘。
- 视野完全封闭前给玩家明确的声音和视觉提示。
- 进入全封闭 VR 后继续遵守系统安全边界，不因视觉封闭而降低物理安全要求。

## 16. 多人同步

多人体验使用服务端或房主统一时间：

```text
Server: Prepare VR
Clients: Load and report Ready
Server: Broadcast transition start time
Clients: Animate from shared network time
Clients: Report full occlusion
Server: Commit VR state
Clients: Disable Passthrough and finalize
```

需要同步的不是每一帧半径，而是：

- 转场类型。
- 遮罩中心和方向。
- 开始网络时间。
- 持续时间和曲线参数。
- 最终 VR 状态版本。

## 17. 验收清单

- [ ] VR 内容加载完成前不会关闭 Passthrough。
- [ ] 关闭 Passthrough 时视野已被完全不透明内容覆盖。
- [ ] 转场期间地面高度和世界方向不跳变。
- [ ] Passthrough 开关延迟不会造成黑色或透明空帧。
- [ ] PICO 与 Quest 的视觉时序一致。
- [ ] 径向、扫描和高度遮罩在双眼中表现一致。
- [ ] 转场完成后临时 Shader、粒子和透明层已关闭。
- [ ] 连续执行 MR → VR → MR 不发生内存持续增长。
- [ ] 多人客户端在约定网络时间进入相同状态。
- [ ] 加载失败和超时具备安全恢复路径。

## 18. 决策摘要

本项目默认采用以下决策：

- Passthrough 只通过平台适配层开关，不直接承担视觉转场。
- VR 世界通过不透明几何和 Shader 遮罩逐渐显现。
- 默认表现为地面重构 + 径向消融 + 穹顶封闭。
- 虚实差异较大时增加雾化遮挡。
- 黑场或光幕作为加载超时和失败的兜底方案。
- 转场结束后关闭所有临时渲染开销。
- 多人转场由共享网络时间统一驱动。
